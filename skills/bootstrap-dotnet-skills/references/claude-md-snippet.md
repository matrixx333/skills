# CLAUDE.md routing block

How to generate the skills-routing block written into the invoking project's `CLAUDE.md`.

Adapted from [upstream's suggested AGENTS.md / CLAUDE.md snippet](https://github.com/Aaronontheweb/dotnet-skills#suggested-agentsmd--claudemd-snippets),
with three deliberate departures — see *Departures from upstream* below.

---

## Source of truth

Skill names come from what's actually installed under `--scope` — nothing else. Get names and
descriptions with:

```bash
bash <skill-dir>/scripts/install-skills.sh --emit-catalog --scope <the scope you installed into>
```

That returns `{name, description}` per installed skill (plus the source `repo`/`ref`/`commit`),
read directly from each installed skill's frontmatter. Use it instead of opening the skills
themselves; they are 10–40KB each.

## Departures from upstream

1. **Names must be directory names, not frontmatter names.** Upstream's published snippet (this
   repo's `dotnet-skills/` is a vendored copy of
   [Aaronontheweb/dotnet-skills](https://github.com/Aaronontheweb/dotnet-skills)) lists
   `api-design`, `dotnet-project-structure`, `testcontainers-integration-tests`,
   `mailpit-integration`, `dependency-injection-patterns`, `modern-csharp-coding-standards`,
   `dotnet-slopwatch`, `dotnet-local-tools`, `type-design-performance`, and
   `OpenTelemetry-NET-Instrumentation`. Claude Code routes by **directory name**, and for ten of our
   skills the two differ — those names would route to nothing. Use `--emit-catalog`'s `name` field
   (a directory name), not any frontmatter name mentioned in a skill's own prose.
2. **Only what's actually installed.** Upstream documents ~30 skills; this repo vendors a subset —
   every `akka-*` skill, plus `playwright-blazor`, `playwright-ci-caching`, `r3-reactive-extensions`,
   `marketplace-publishing`, and `skills-index-snippets` were never vendored here, so they can't
   appear in the catalog and must not appear in the routing block either. A caller's
   `--skills`/`--exclude` can narrow the installed set further for one target project — the routing
   block should only ever list what `--emit-catalog` actually reports for that install.
3. **No agent personas.** Upstream lists five (`akka-net-specialist`, `docfx-specialist`,
   `dotnet-benchmark-designer`, `dotnet-concurrency-specialist`, `dotnet-performance-analyst`). This
   repo installs no agents, so a reference to them is a dead pointer.

## Invariants

- Every name in the block resolves to a directory in the install scope. Verify before writing.
- Categories with no surviving skills are dropped entirely, not left with an empty list.
- The block never mentions Akka.NET or xUnit — both were already stripped from these skills when
  they were vendored into this repo (see `CLAUDE.md`), so routing that named them would contradict
  their content.

---

## Structure

Write exactly this shape, filling categories from the catalog. Keep it compact — it is loaded into
context on every session in the target project.

````markdown
<!-- BEGIN skills-routing (generated by bootstrap-dotnet-skills) -->
## .NET skill routing

IMPORTANT: Prefer retrieval-led reasoning over pretraining for .NET work.
Workflow: skim repo patterns -> consult the skill by name -> implement the smallest change -> note conflicts.

- **Aspire:** aspire-configuration, aspire-integration-testing, aspire-mailpit-integration, aspire-service-defaults
- **C# language & API:** csharp-coding-standards, csharp-api-design, csharp-concurrency-patterns, csharp-type-design-performance
- **Data:** efcore-patterns, database-performance
- **DI & configuration:** microsoft-extensions-dependency-injection, microsoft-extensions-configuration
- **Testing:** unit-tests, testcontainers, snapshot-testing, verify-email-snapshots
- **Ecosystem:** project-structure, package-management, local-tools, serialization, opentelementry-dotnet-instrumentation, dotnet-devcert-trust, ilspy-decompile, mjml-email-templates
- **Quality gates:** slopwatch, crap-analysis
- **Design:** design-patterns

### Routing rules

- **Writing or refactoring unit tests → `unit-tests`.** It owns test structure: fluent data builders,
  composition-root harnesses, and the loop to 100% line/branch/method coverage. It reads
  `.claude/rules/testing.md` for this project's framework and libraries.
- **Integration tests against real infrastructure → `testcontainers` or `aspire-integration-testing`.**
  Those use real containers instead of mocks; `unit-tests` uses mocks and a harness. Pick by the kind
  of test, not by preference.
- **Coverage risk triage → `crap-analysis`.** It complements the `unit-tests` coverage loop rather
  than replacing it: `crap-analysis` finds which code is worth testing, `unit-tests` writes the tests.
- **NUnit is this project's test framework.** These skills were rewritten from xUnit on install.
- **Akka.NET is not used here** and was stripped from these skills. Do not reintroduce it.
<!-- END skills-routing -->
````

Adjust the category lists to whatever `--emit-catalog` actually reports for that install — the
block above reflects a full default install, not a fixed roster.

## Writing it

1. Locate the target `CLAUDE.md` in the invoking project (cwd). If none exists, create it with a
   `# CLAUDE.md` heading and the standard one-line preamble before appending.
2. **Match markers as whole lines, never as substrings.** A marker is a line whose entire content is
   the comment. Documentation *about* this mechanism often quotes the marker text inline — matching a
   substring would treat that prose as the opening marker and delete everything between it and the
   real closing marker. Anchor on `^<!-- BEGIN skills-routing` and `^<!-- END skills-routing -->$`.
3. If both markers are present as whole lines, replace everything **between** them, leaving the
   markers in place.
4. If they are absent, append the whole block (markers included) at the end of the file.
5. If either marker appears more than once as a whole line, stop and report it rather than guessing
   which pair is authoritative — that is a corrupted file, not something to repair silently.
6. Never write the block twice, and never modify a byte outside the markers. Re-running the skill
   must leave the rest of `CLAUDE.md` untouched.
7. Report to the user which file was written and whether it was an insert or a replace.
